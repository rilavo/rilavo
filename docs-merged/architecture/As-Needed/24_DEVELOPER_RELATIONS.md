# Rilavo Product — Developer Relations (E-24)

**Tree:** Product
**Wave:** Continuous / As-Needed
**Status:** Decided
**Depends on:** E-07
**Closes when:** Ongoing, never fully closed — this is a standing function once it exists, not a project with an end state.

## What this function actually is, distinguished from two things it's easy to mistake it for

**Not marketing (E-23):** marketing pushes messages outward; developer relations responds to and builds trust with a technical audience that's already engaged. **Not the free-tier product itself (E-07):** the product's free tier is self-serve by design — docs, SDK, sandbox, no human required. Developer relations is the human layer around that product, not a substitute for making the product good enough to need less of it.

## Concrete activities

Responding quickly in public developer venues — GitHub issues, community forums, wherever the wedge audience (P-03) already gathers. Publishing real, specific incident postmortems (E-13) rather than vague "we experienced an issue" statements — a postmortem that names what actually broke and what changed as a result builds more trust than one that doesn't. Maintaining SDK quality as an ongoing practice, not a one-time deliverable (P-20).

## Worked example — a postmortem as a trust-building act, not just disclosure

Following a Sev1 incident (P-23, E-13), a public postmortem names the actual root cause, the actual timeline, and the actual change made as a result — not a generic reassurance. A developer evaluating whether to depend on Rilavo learns more from reading one honest, specific postmortem than from any amount of marketing copy about reliability, because the postmortem is falsifiable and the marketing copy isn't.

## Why this is a trust-building function, not a growth-hacking one

The wedge audience (P-03) is technical and skeptical by nature — the same audience that would disqualify a vague sales pitch (E-18's own edge case) reacts the same way to developer-relations activity that reads as promotional rather than substantive. This function only works if it's genuinely useful to developers independent of whether it drives adoption, which is precisely why it's decided as a distinct function here rather than folded into marketing.

## What would change this decision

Evidence that public developer-channel engagement isn't actually influencing integration decisions — at which point this document's premise would need revisiting, though no such evidence exists yet since the function hasn't operated at real scale.
