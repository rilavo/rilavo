# Rilavo Product — Go-to-Market (E-18)

**Tree:** Product
**Wave:** 3 — Commercial Core
**Status:** Decided
**Depends on:** E-04, E-05
**Closes when:** Revisited if segments 1–2 (E-04) don't convert as expected — this plan is a hypothesis with a defined test window, not a fixed roadmap.

## Developer-led and product-led first — the one non-negotiable

Not product-sales-led. The wedge audience (P-03) is technical and reachable through documentation and direct outreach, without paid advertising — a sales-led motion aimed at this audience first would be optimizing for the wrong buyer before the right one has even been tested.

## A concrete first-90-days plan

**Days 1–30:** direct, specific outreach to teams already living the problem — MCP server operators and agent-platform builders with unmanaged or unauthenticated traffic, identifiable precisely because the authentication gap (P-01, P-03) is a documented, current fact, not a persona guess. Channels: developer communities already discussing agentic tooling, GitHub issues and discussions on relevant open-source agent frameworks, direct technical outreach — not a press push, not paid acquisition.

**Days 30–60:** the first pilot integrations become the actual product-development input, not just a sales metric. Every friction point a real developer hits during integration feeds directly back into the SDK (P-20) and API (P-19) documents — this phase is deliberately as much engineering feedback as sales pipeline.

**Days 60–90:** the first test of whether the distribution loops (E-19) are real rather than assumed — specifically, whether a verifier's adoption is creating any organic pull toward issuance from developers who need to reach that verifier, without additional outreach.

## Worked example — what day-1 outreach actually looks like

Not "check out our trust infrastructure platform." Closer to: "your MCP server is one of the roughly 38–40% currently running without authentication — here's a drop-in SDK that adds it in an afternoon." Specific, falsifiable, and aimed at a fact the prospect can verify about their own systems in the same conversation — the same discipline set in E-03's customer-problem framing, applied here as the actual first message.

## Edge case — a prospect in segment 1–2 who doesn't recognize the problem

**Decided:** this is a disqualifying signal, not a persuasion challenge. If a technical team doesn't recognize unmanaged agent-authorization as a live concern once shown the evidence, they're not this wedge's first customer yet — better to move to the next prospect than to spend the 90-day window convincing someone the problem exists, which the evidence (P-01, P-03) should already be doing on its own.

## What would change this plan

If days 1–60 produce engagement but no real pilot conversions, that's a signal the message or channel is wrong, not that developer-led motion itself is wrong — the fix is in this document, not a premature pivot to product sales (E-22) before the developer-led path has had a real test.
